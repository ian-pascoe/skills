### GitHub gotchas

- **Bypass flag: `--admin`** ("Use administrator privileges to merge a pull request that does not meet requirements"). Never pass it. With a merge queue it also skips the queue (`gh pr merge --help`).
- **Auto-merge flag: `--auto`** ("merge only after necessary requirements are met"); `--disable-auto` undoes it.
- **Implicit auto-merge with a merge queue.** For a base branch that requires a merge queue, "no merge strategy is required. If required checks have not passed, auto-merge will be enabled. If passed, the PR is added to the merge queue" (`gh pr merge --help`). So a plain `gh pr merge` may queue instead of merging. Check the result (`gh pr view --json state,autoMergeRequest`) and don't assume "merged".
- `--delete-branch` also deletes the local branch (`gh pr merge --help`).
- `gh pr checks` exits 1 when a PR has no checks at all (https://github.com/cli/cli/issues/9390; a first-party issue, SECONDARY for current behaviour). Right after a push the checks may not be registered yet, so distinguish "no checks reported" from "failed".
- `gh run watch` does not work with fine-grained PATs (needs `checks:read`) (https://cli.github.com/manual/gh_run_watch). `gh pr checks --watch` is the safer choice.
- REST `PUT /pulls/{n}/merge` "does not support stacked pull requests or merging with a merge queue" (https://docs.github.com/en/rest/pulls/pulls). Use `gh pr merge`, not raw REST.
- Review-thread resolution is GraphQL-only. Keep a canned query.
- `gh stack merge` is all-or-nothing and "You cannot bypass merge requirements when you merge stacked pull requests"; it queues if a merge queue is on and ignores method flags then (https://docs.github.com/en/pull-requests/reference/stacked-prs-cli-commands).
- `gh pr merge` asks GraphQL, not REST: it skips auto-merge only when the PR is already `CLEAN`/`HAS_HOOKS`/`UNSTABLE` (`autoMerge: opts.AutoMergeEnable && !isImmediatelyMergeable(...)`), and exits with "the base branch policy prohibits the merge" on `BLOCKED` unless `--admin` (source above). Don't pass `--admin`; re-check `viewerCanMergeAsAdmin` if the agent's token belongs to an admin, since an admin merge through another path (REST/GraphQL directly) would not hit this client-side guard.

### GitLab gotchas

- **CONFIRMED: `glab mr merge` enables auto-merge by default.** Docs synopsis: "When a pipeline is running, auto-merge is enabled by default. Pass `--auto-merge=false` to merge immediately." Flag `--auto-merge  Set auto-merge. (default true)` (https://docs.gitlab.com/cli/mr/merge/). Source confirms (`internal/commands/mr/merge/mr_merge.go`): `BoolVarP(&opts.setAutoMerge, "auto-merge", "", true, …)`. Behaviour: when the MR has a pipeline, `AutoMerge=true` is sent to the Accept-MR API, so the MR is queued as "merge when pipeline succeeds" instead of merging. In a TTY with neither flag given it prompts "Set auto-merge?". Non-interactive runs get the default `true`. Only on that auto-merge path does glab refuse a `failed`/`canceled` pipeline ("Cannot perform merge action"); with `--auto-merge=false` that guard is skipped (see below). **Disable with `--auto-merge=false`.**
- The deprecated alias `--when-pipeline-succeeds` also defaults true. Don't use it.
- **`--auto-merge=false` + "Pipelines must succeed" OFF ⇒ merges immediately, even with a running or failed pipeline (CONFIRMED in source).** `--auto-merge=false` sends no `auto_merge`, so the API takes the `elsif merge_request.mergeable?` branch and merges now (`lib/api/merge_requests.rb`, https://gitlab.com/gitlab-org/gitlab/-/raw/master/lib/api/merge_requests.rb). `mergeable?` includes `CheckCiStatusService`, whose `execute` returns `inactive` unless `merge_request.auto_merge_enabled? \|\| only_allow_merge_if_pipeline_succeeds?` (https://gitlab.com/gitlab-org/gitlab/-/raw/master/app/services/merge_requests/mergeability/check_ci_status_service.rb). So with the project setting off and no auto-merge, the CI check is skipped. glab's own guard only trips when `detailed_merge_status == "ci_must_pass"` or when auto-merge is already set and the pipeline isn't `success` (`internal/commands/mr/mrutils/mrutils.go`). With the setting ON, a non-success pipeline gives 405 ("cannot merge"). **Landing must wait for CI itself and check `detailed_merge_status == mergeable` before `--auto-merge=false`.** Discussions-must-be-resolved and approvals are separate checks in the same `mergeable?` and still apply.
- **Merge trains (CONFIRMED from source + docs).** `merge_train_enforcement` (`GET /projects/:id`; GA 19.3; "no effect unless merge trains are enabled"): `allow_bypass`, `enforce_for_all_users`, `enforce_with_owner_override`. With the project enforcing trains, `--auto-merge=false` is **rejected** (405): the EE API override `validate_immediate_merge!` raises "This project requires merge requests to go through the merge train. Set auto_merge to true to add this merge request to the train." (`ee/lib/ee/api/merge_requests.rb`). With trains enabled but `allow_bypass`, `--auto-merge=false` **merges immediately and skips the train** (docs: "Merge immediately … ignoring the status of the merge train… The merge train pipelines for all other merge requests on the train are canceled", https://docs.gitlab.com/ci/pipelines/merge_trains/); an optional `skip_merge_train` param exists. **Non-bypassing call on a train project: `glab mr merge <n> --squash --sha <head> --yes` with the default `--auto-merge`** (API `auto_merge=true`) which joins the train (or merges when checks pass). Since **GitLab 19.1** (flag `fix_merge_api_train_bypass`, removed in 19.1) `auto_merge` requests are routed to the train; on self-managed < 19.1 the API call may bypass the train (https://docs.gitlab.com/api/merge_requests/). Then poll `state`/`merge_when_pipeline_succeeds`; the MR merges later, not at call time. Detect trains first: `glab api projects/:id --jq '{t:.merge_trains_enabled,e:.merge_train_enforcement,p:.only_allow_merge_if_pipeline_succeeds}'`.
- No admin-bypass flag in `glab mr merge` or in the Merge API's attribute list (`auto_merge`, `sha`, `squash`, `should_remove_source_branch`, `merge_commit_message`, `squash_commit_message`). `--sha` is mutually exclusive with `--rebase` in source. A group/instance setting can make `sha` mandatory on the merge API (GitLab 19.2).
- Methods: default = merge commit; `--squash`; `--rebase` (rebases first; mutually exclusive with `--squash`). Project-level merge method (e.g. fast-forward) may constrain these (**UNVERIFIED** against glab).
- **`glab mr note create` makes a resolvable discussion thread by default.** For an informational comment use `--resolvable=false`, or it can block merge under "All threads must be resolved" (docs for `mr note create`).
- `glab ci status` works by branch, not the MR's head pipeline; for MR/detached/fork pipelines use `glab ci get --merge-request`.
- `mr note` list/create/resolve are flagged "experiment … might be unstable or removed". Pin a fallback to `glab api`.
- `--remove-source-branch` on merge: in `create`, "omit to use project settings".

### Bitbucket Cloud gotchas

- **No bypass or auto-merge parameter** in the merge API spec (full swagger searched: `pullrequest_merge_parameters` has only `message`, `close_source_branch`, `merge_strategy`). **But enforcement is weak off-Premium:** merge checks only warn (see row l), so the API merge can succeed with failing checks. **The landing flow must gate on `mergeability/checks` (`blocking`), commit statuses and approvals itself; do not rely on the 4xx from the merge call.**
- **Merge queue:** if the destination has an active merge queue, merge "is added to the queue instead" and returns **202** with a polling `Location` (task-status API `GET …/merge/task-status/{task_id}`) even if `async=false`. Don't treat 202 as merged.
- `close_source_branch` omitted ⇒ "falls back to the value used when the pull request was created, which defaults to False". Set it explicitly on create or merge.
- No head-SHA pin on merge (unlike GitHub/GitLab); mitigate by re-reading `source.commit.hash` and `mergeability/checks` just before merging.
- `async` merge can time out into a 202; poll task-status.
- Commit statuses aggregate CI from Pipelines and third parties; there is no single "checks" rollup endpoint beyond `…/statuses`.

### Bitbucket Data Center (brief)

Different product, different API: `https://<host>/rest/api/latest/projects/{KEY}/repos/{slug}/pull-requests…` (docs: https://developer.atlassian.com/server/bitbucket/rest/v1004/api-group-pull-requests/). The page is JS-rendered and my fetch captured only fragments. A search excerpt shows merge needs a `"version"` in the body (optimistic locking) and that "Forge and OAuth2 apps cannot access" some resources. No official CLI found. Everything else about DC (auth, merge/decline paths, comments, resolve semantics) is **UNVERIFIED**; research separately if DC support is required.

### Azure DevOps gotchas

- **Bypass: `--bypass-policy true`** (+ `--bypass-policy-reason`) on `create` and `update` ("Bypass required policies (if any) and completes the pull request once it can be merged"). Never pass it. REST equivalent `completionOptions.bypassPolicy`.
- **Auto-merge: `--auto-complete true`** on `create`/`update` ("complete automatically when all policies have passed"). Default False. REST: "Auto-complete always waits for required policies (isBlocking == true)" but optional policies can be skipped via `autoCompleteIgnoreConfigIds`.
- **Completion semantics (CONFIRMED from extension source + REST docs).** (1) `az repos pr update --status completed` first GETs the PR, then PATCHes with `last_merge_source_commit = existing_pr.last_merge_source_commit` (and the existing completion options if none passed) (`pull_request.py`). So the CLI **re-sends the server's own current `lastMergeSourceCommit`; it is not a pin to the head you reviewed.** The REST docs describe `lastMergeSourceCommit` only as "the commit at the head of the source branch at the time of the last pull request merge" (https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/update?view=azure-devops-rest-7.1); **whether the server rejects a mismatching value is UNVERIFIED** (not documented). Do your own pin: read `lastMergeSourceCommit.commitId` (and your local `git rev-parse <branch>` / pushed head) immediately before, abort if it differs from the reviewed head, and for a real server-side pin send the REST PATCH with your commit id yourself. (2) **Completion is asynchronous**: `mergeStatus` has `queued`, `succeeded`, `conflicts`, `rejectedByPolicy`, `failure`; poll `az repos pr show` until `status == completed` and `lastMergeCommit` is set, or `mergeStatus` is a failure value (docs above). (3) Policies are enforced unless `bypassPolicy` is sent (row l); policy rejection text **UNVERIFIED**.
- CLI squash is a boolean only. Other strategies (`noFastForward` default, `squash`, `rebase`, `rebaseMerge`) need REST `completionOptions.mergeStrategy`. If `mergeStrategy` is unset, `squashMerge` decides (deprecated) (GitPullRequestMergeStrategy enum on the update page).
- Squash merges **do not** trigger commit-keyword work-item resolution on completion (above).
- Comment/thread work needs REST via `az devops invoke`; `invoke` parses `--api-version` as a number (SECONDARY note: use `7.1`, not `7.1-preview.4`).
- Branch names in REST are full refs (`refs/heads/x`); CLI flags take short names.

### Gitea/Forgejo gotchas

- **Bypass-capable server fields:** merge API has `force_merge` (admin override) and `merge_when_checks_succeed` (auto-merge/schedule) plus `delete_branch_after_merge` and `head_commit_id` (SHA pin) (`MergePullRequestOption` in both swaggers). `DELETE /repos/{o}/{r}/pulls/{n}/merge` cancels a scheduled auto-merge. **`gt`: `--auto` = "Merge once the required checks succeed"; avoid.** `gt`/`tea`/`fj` expose no force-merge flag (and raw `force_merge` is the only admin skip, see below) (source-checked: `gt` source grep for force/bypass/admin in merge code found none; `tea`, `fj` send null/unset).
- `fj pr merge --method manual` = Gitea's `manually-merged`: marks the PR merged without merging. `gt` docs: `--method manually-merged --commit SHA` "marks it as merged by that commit … Gitea does not check that the commit contains the pull request's changes." **Never use** in landing.
- **Admins vs branch protection (CONFIRMED in Forgejo source; Gitea docs agree).** Protections can be skipped **only when the merge request sets `force_merge: true`** (`CheckPullMergeable(..., form.ForceMerge, ...)`: its `adminSkipProtectionCheck` is the only skip, https://codeberg.org/forgejo/forgejo/raw/branch/forgejo/services/pull/check.go and `routers/api/v1/repo/pull.go`). Then an **instance admin always** skips, and a **repo admin skips unless the rule has `apply_to_admins`** (default `false`: `ApplyToAdmins bool … DEFAULT false`, `models/git/protected_branch.go`). Gitea: "Administrators must follow branch protection rules removes the ability for repository administrators to bypass the rules with the 'Force merge' button" (`block_admin_merge_override`; https://docs.gitea.com/usage/access-control/protected-branches); Gitea dev API also has `enable_bypass_allowlist` + `bypass_allowlist_usernames/teams` (semantics UNVERIFIED). **`gt`, `tea` and `fj` never send `force_merge`, so an admin token is still gated; the risk is only raw REST/`tea api` calls that pass `force_merge`.** Auto-merge scheduling (`merge_when_checks_succeed`) skips the protection check at schedule time and enforces when it fires (`MergeCheckTypeAuto` branch in the same function; firing-time enforcement not read). Read a rule: `GET /repos/{o}/{r}/branch_protections/{name}` (fields `required_approvals`, `enable_status_check`, `status_check_contexts`, `block_on_rejected_reviews`, `enable_merge_whitelist`, `apply_to_admins`/`block_admin_merge_override`; likely needs admin, UNVERIFIED).
- `tea pr merge` defaults to a **merge commit** and has no branch-delete; `gt pr merge` without a method uses the repo default or prompts: always pass the method.
- Tea/gt/fj `--repo` and login discovery from the git remote can pick the wrong login when several instances are configured: pass `--login/--host`.
- Review-thread resolve exists in Gitea's dev API and `gt`/`tea`, not in Forgejo.
- `gt` requires Gitea 28+; older self-hosted Gitea must use `tea` or REST.

### GitCafe gotchas

- **No bypass or auto-merge flag on `pr merge`** (`cafe pr merge --help`: only `--strategy`, `--operation`, `--wait`). The merge API body is `{requestId, expectedVersion, headOid, baseOid, strategy}` (OpenAPI), i.e. the head/base are pinned; the CLI "stops with a CONFLICT" if head/target changed. No `--delete-branch` flag: branch deletion comes from the repo setting "Automatically delete head branches" (https://git.cafe/docs/pull-requests/merge.md).
- **Always pass `--strategy squash`:** "without the flag, the first method allowed by pull status is used."
- **Rulesets can have "bypass actors" and `cafe pr merge` has no way to refuse the bypass.** See row l: a `pull_request`-mode bypass actor skips the rules on merge. `cafe repo ruleset effective <branch>` is the pre-flight; if it says you can bypass, gate on `cafe pr status` yourself (required checks passed, approvals present) before calling merge.
- Merges are asynchronous ("accepted first and finish later"); `pr merge` waits up to 30 s then errors with an operation ID; don't blind-retry (`MERGE_IN_PROGRESS`). Retry with the same `requestId`.
- **Stack members cannot be merged singly**: "Members of a stack merge through the stack with `cafe stack merge`". Landing is durable and sequential, **not all-or-nothing** (unlike `gh stack merge`): "If a later member becomes blocked, already merged members remain merged." Always `--dry-run` first. After squash/rebase landing, the next PR is rebased and its checks re-evaluated, so landing may stop awaiting checks.
- In a stack, `pr edit --base` doesn't apply; the base follows the stack. When a stack lands, other unstacked PRs targeting a landed member branch auto-move to the landing base.
- Repos mirrored from GitHub: GitCafe **writes comments/merges through to GitHub** and "GitHub performs the merge"; GitHub's rules still apply; `cafe pr status` may report "Waiting on GitHub's conflict check".
- `cafe pr ready` = merge-readiness against rulesets, **not** "mark ready for review" (that is `cafe pr undraft`).
- `pr comment --path/--line` inline comments do not belong to a review.
- Token scope: attachments need `repo attachments/write`.

`cafe skills list|show|install` ships agent skills embedded in the CLI (https://git.cafe/docs/reference/cli.md; "installs ready-made skills that teach coding agents how to use `cafe`").
